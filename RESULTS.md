# RESULTS.md

## Практична робота № 4
### Тема: Побудова REST API з використанням маршрутизатора Chi

## 1. Результат виконання

Розроблено консольний вебсервіс **Device Registry API** для реєстрації та керування мережевими пристроями.

Реалізовано всі три рівні практичної роботи:

- доменну модель `Device`;
- in-memory репозиторій з `sync.RWMutex`;
- `GET`, `POST`, `PUT`, `DELETE`;
- маршрутизатор `go-chi/chi/v5` із суб-роутером `/api/v1/devices`;
- параметри шляху через `chi.URLParam`;
- фільтрацію `status` і `type`;
- Logger Middleware;
- Panic Recovery Middleware;
- CORS Middleware;
- стандартизований JSON-формат помилок;
- коректні HTTP-коди відповіді.

## 2. Структура проєкту

```text
internal/domain       — моделі Device і Problem
internal/repository   — інтерфейс і потокобезпечне сховище
internal/handler      — REST HTTP-обробники
internal/middleware   — Logger, Recoverer, CORS
cmd/server            — точка запуску сервера
```

## 4. Перевірені сценарії

### Створення

`POST /api/v1/devices` повертає `201 Created` та JSON створеного пристрою.

### Отримання списку

`GET /api/v1/devices` повертає `200 OK` та масив пристроїв.

### Фільтрація

`GET /api/v1/devices?status=online` повертає тільки пристрої зі статусом `online`.

`GET /api/v1/devices?type=sensor` повертає тільки пристрої типу `sensor`.

### Отримання за ID

`GET /api/v1/devices/dev-001` повертає `200 OK`, якщо ресурс існує, або `404 Not Found`.

### Оновлення

`PUT /api/v1/devices/dev-001` повертає `200 OK`, оновлює поля пристрою та `updated_at`.

### Видалення

`DELETE /api/v1/devices/dev-001` повертає `204 No Content`. Повторне читання ресурсу повертає `404 Not Found`.

## 5. Стандартизована помилка

При зверненні до неіснуючого ресурсу формується JSON:

```json
{
  "error": "Not Found",
  "message": "Device with ID 'unknown-device' does not exist in registry",
  "status": 404,
  "timestamp": "2026-10-07T00:00:00Z"
}
```

## 6. Middleware

Logger фіксує віддалену адресу, HTTP-метод, шлях, статус і тривалість запиту.

Panic Recovery перехоплює паніку через `recover()`, записує стек викликів і повертає `500 Internal Server Error` замість аварійного завершення сервера.

CORS додає `Access-Control-Allow-Origin: *`, дозволені HTTP-методи та заголовки. OPTIONS-запит завершується статусом `204 No Content`.

## 7. Потокобезпечність

Репозиторій використовує `sync.RWMutex`. Операції читання виконуються під `RLock()`, а створення, оновлення та видалення — під ексклюзивним `Lock()`. Це запобігає конкурентному доступу до `map` із небезпечною модифікацією.

## 8. Контрольні питання

### 1. Чим REST відрізняється від RPC?

REST працює з ресурсами та їх URI, а операції визначаються стандартними HTTP-методами. RPC більше орієнтований на виклик конкретних процедур або команд.

### 2. Safe та idempotent методи

Safe-метод не повинен змінювати стан сервера. Idempotent-метод після повторення має той самий результат стану. GET є safe та idempotent, POST — не safe і зазвичай не idempotent, PUT та DELETE — idempotent.

### 3. Переваги Chi та Radix Tree

Chi зручно підтримує параметризовані маршрути, суб-роутери та middleware, залишаючись сумісним із `net/http`. Radix Tree — дерево, у якому спільні частини ключів або шляхів використовуються спільно для ефективного пошуку маршруту.

### 4. Навіщо `sync.RWMutex`?

Звичайна `map` не є безпечною для одночасного читання і запису. `RWMutex` дозволяє паралельні читання, але блокує доступ під час зміни даних.

### 5. Коли використовується `204 No Content`?

Коли операція успішна, але сервер не має повертати представлення ресурсу, наприклад після DELETE. Така відповідь не повинна містити HTTP-body.

### 6. Як працює `next.ServeHTTP`?

Middleware виконує свою логіку, викликає `next.ServeHTTP(w, r)` для передачі запиту наступному обробнику, а після його завершення може виконати логіку після обробки.

### 7. Як `recover()` захищає сервер?

`recover()` викликається у `defer` та перехоплює паніку в поточній горутині. Middleware може залогувати помилку і повернути клієнту `500`, не завершуючи весь процес сервера.

### 8. Що таке CORS?

CORS — механізм браузера, який контролює міждоменні HTTP-запити. Сервер через спеціальні заголовки повідомляє браузеру, з яких джерел, методів і заголовків дозволені такі запити.
